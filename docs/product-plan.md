# Product Plan

## 产品定位

`repo-auto-puller` 不应停留在“定时执行 `git pull` 的脚本”，而应产品化为一个本地优先的“仓库自动同步助手”。

目标用户：

- 独立开发者
- 需要多机器同步代码的工程师
- 小团队里的个人开发环境

核心价值：

- 让常用仓库尽量保持最新
- 默认不破坏本地现场
- 让用户清楚知道“为什么这次没拉”

交付形态：

- 第一阶段：本地 daemon + CLI
- 第二阶段：桌面壳层
- 第三阶段：再评估团队版和云配置

## 为什么做成本地产品

这个产品更适合作为本地软件，而不是纯云端服务：

- 需要直接访问本机 Git 仓库
- 需要依赖本机 SSH key、Git credential helper、HTTPS token
- 需要感知未提交改动、本地领先、分叉状态
- 需要和系统级能力集成，如通知、开机自启、后台常驻

## 当前状态

截至 `v0.1.3`，已经完成：

- Rust workspace：`crates/core` + `crates/cli`
- 多仓库配置模型
- `init`、`status`、`check-config`、`install-service`
- 失败钩子
- Linux `systemd` / macOS `launchd` 服务安装辅助
- GitHub Actions CI
- GitHub Releases 自动发布
- Linux/macOS 安装脚本
- 预编译产物覆盖 Linux `x86_64`/`aarch64` 与 macOS `x86_64`/`aarch64`

这意味着“单机可安装、可后台运行、可解释状态”的基础产品已经成立，后续重点不再是从零做功能，而是补齐运维能力、平台覆盖和用户体验。

## 开发节奏

后续开发按固定循环推进，每一轮只做一个足够小的增量：

1. 先确定一个明确切片
2. 只实现这个切片，不顺手扩散需求
3. 做对应验证
4. 测试通过后提交
5. 推送到远端
6. 再进入下一个切片

每一轮的验收最少包括：

- `cargo fmt --all --check`
- `cargo test --workspace`
- `cargo clippy --workspace --all-targets -- -D warnings`
- 如果改了安装脚本：`bash -n scripts/install.sh`
- 如果改了发布流程：至少验证一次 workflow 或 release 结果

## 版本拆分

### v0.5 运行时硬化

目标：把“能跑”推进到“长期跑得住、升级不容易出坑”。

建议按下面顺序拆分：

1. `version` / `--version` 与发布信息核对流程固定化
2. 增加 `uninstall-service`，让用户能干净回滚
3. 增加 `self-check` 或 `doctor`，诊断 Git、网络、凭据、服务状态
4. 增加更明确的退出码和机器可读错误
5. 升级 GitHub Actions 依赖，处理 Node 20 弃用告警

完成标准：

- 用户可以安装、检查、卸载、重装
- 发布流程没有明显的供应链和兼容性警告
- 常见故障能被 CLI 主动解释

### v0.6 同步策略增强

目标：让自动拉取更可控，而不是只会“开或不开”。

建议切片：

1. 分支白名单
2. 仓库级暂停开关
3. 静默时段 / 暂停窗口
4. 拉取前后 hook
5. 更细的失败分类

完成标准：

- 用户能控制哪些仓库、哪些分支允许自动拉取
- 不再只能靠改配置文件的 `enabled` 做粗粒度停用

### v0.7 可观测性

目标：让用户和代理能更快定位“没拉成功”的原因。

建议切片：

1. 结构化日志格式
2. 最近一次同步结果持久化
3. `status --json`
4. 历史记录文件
5. 桌面通知抽象层

完成标准：

- `status` 既适合人看，也适合代理或外部工具消费
- 失败原因不再只留在滚动日志里

### v0.8 平台补齐

目标：把“Linux/macOS 可用”推进到“主流桌面平台都可部署”。

建议切片：

1. Windows 平台能力评估
2. Windows 后台任务安装辅助
3. Windows 安装文档
4. 平台差异测试矩阵补齐

完成标准：

- 三大桌面平台都有明确安装路径
- 平台支持矩阵和实际发布矩阵一致

### v0.9 桌面外壳

目标：开始提供非 CLI 用户可用的入口。

建议切片：

1. 只读状态页原型
2. 最后同步时间和失败原因展示
3. 一键暂停 / 恢复
4. 托盘或菜单栏入口

完成标准：

- 普通用户不看日志也能理解当前状态

### v1.0 稳定版

目标：把产品从“工程师工具”推进到“可长期交付的软件”。

建议切片：

1. 稳定配置迁移
2. 自动更新或升级说明
3. 完整手册和故障排查文档
4. 安装包与签名策略
5. 长周期回归测试

完成标准：

- 新用户能稳定安装
- 代理能稳定代装
- 长期运行和升级有明确边界

## 下一阶段执行顺序

后续建议严格按这个优先级继续：

1. 先做 `v0.5.1`：`uninstall-service`
2. 再做 `v0.5.2`：`doctor` / `self-check`
3. 再做 `v0.5.3`：CI / release action 升级，消除 Node 20 弃用告警
4. 再做 `v0.5.4`：机器可读状态输出，如 `status --json`
5. 再进入 `v0.6`

这样安排的原因是：

- 先补运维闭环，避免“装得上但不好撤”
- 再补诊断，减少现场排查成本
- 再补发布链稳定性，避免后续版本继续积累流程债
- 最后再做更强的用户能力

## 商业化模型

适合从本地工具切入，再按能力分层：

- Free：基础自动拉取、单机后台运行、状态检查
- Pro：多仓库高级规则、通知、历史记录、安装辅助增强
- Team：策略下发、Webhook 告警、审计和团队管理

## 成功标准

这个产品是否成立，不看代码是否优雅，而看以下指标：

- 用户是否敢一直开着它
- 它是否从不破坏用户现场
- 用户是否能快速理解“为什么这次没拉”
- 多仓库场景下是否仍然稳定
- 是否能顺利安装、开机自启、长期运行
