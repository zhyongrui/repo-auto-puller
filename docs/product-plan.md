# Product Plan

## 产品定位

`repo-auto-puller` 不应停留在“定时执行 `git pull` 的脚本”，而应产品化为一个本地优先的“仓库自动同步助手”。

首个产品版本建议定位为：

- 目标用户：独立开发者、多机器同步代码的工程师、小团队成员
- 核心价值：让常用仓库尽量保持最新，同时不破坏本地现场
- 交付形态：本地守护进程 + CLI；桌面 UI 作为第二阶段

## 为什么做成本地产品

这个产品的核心约束决定了它更适合作为本地软件，而不是纯云端服务：

- 需要直接访问本机 Git 仓库
- 需要依赖本机 SSH key、Git credential helper、HTTPS token
- 需要感知未提交改动、stash、本地分支领先/分叉状态
- 需要和系统级能力集成，如通知、开机自启、后台常驻

因此，推荐路线是：

1. 先做 Rust CLI / daemon
2. 再做桌面壳层
3. 最后再决定是否提供团队版和云配置

## MVP 定义

MVP 必须把“安全自动拉取”做扎实，不要一开始堆太多外围功能。

第一阶段必须有：

- 单仓库监听
- 周期性 `fetch`
- ahead / behind 状态判断
- 仅 `ff-only` 自动拉取
- 脏工作区跳过
- 本地领先跳过
- 分叉跳过
- 明确日志输出
- `dry-run` 模式
- `once` 模式
- 开机常驻的部署说明

## 第二阶段

第二阶段可以开始进入“产品感”：

- 多仓库管理
- 配置文件
- 忽略规则
- 分支白名单
- 桌面通知
- 历史记录
- 系统托盘 / 菜单栏状态
- 一键暂停同步
- 凭据诊断

## 第三阶段

如果前两阶段有真实用户，再考虑团队功能：

- 团队统一同步策略
- 拉取失败告警
- Webhook / Slack / 飞书通知
- 审计日志
- 配置分发
- 组织级许可

## 商业化模型

适合从本地工具切入，再按能力分层：

- Free：单仓库、基础自动拉取
- Pro：多仓库、通知、日志、规则、开机自启助手
- Team：策略下发、告警集成、审计和团队管理

## 版本路线图

### v0.1

Rust CLI，覆盖单仓库自动拉取核心逻辑。

### v0.2

加入 TOML 配置文件和多仓库支持。

### v0.3

加入桌面通知和 systemd / LaunchAgent / Windows Task Scheduler 安装辅助。

### v0.4

做桌面 UI 原型，先显示仓库状态、最后同步时间、失败原因。

### v1.0

稳定版，提供安装包、自更新、完整日志和规则管理。

## 成功标准

这个产品是否成立，不看代码是否优雅，而看以下指标：

- 用户是否敢一直开着它
- 它是否从不破坏用户现场
- 用户是否能快速理解“为什么这次没拉”
- 多仓库场景下是否仍然稳定
- 是否能顺利安装、开机自启、长期运行
